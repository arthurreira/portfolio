## O que construí

Um módulo Terraform que provisiona todo o ciclo de vida de um site estático no GitHub Pages — do zero até uma URL com domínio próprio — em um único `terraform apply`. Ele cria o repositório, ativa o Pages, grava o arquivo CNAME do subdomínio e gera um workflow do GitHub Actions para os próximos deploys. Os três sites do hackathon (`register.arthurreira.dev`, `schedule.arthurreira.dev` e `projects.arthurreira.dev`) foram provisionados dessa forma.

## O que aprendi

O provider Terraform do GitHub tem particularidades que não aparecem nos providers de nuvem. A API do GitHub é eventualmente consistente: nem sempre é possível encadear imediatamente a criação do repositório e a ativação do Pages, o que exigiu blocos `depends_on` e `time_sleep` bem planejados. O aprendizado mais profundo foi entender para que IaC realmente serve: não apenas provisionar servidores, mas registrar todo o processo de configuração para que ele possa ser repetido, revisado e removido com segurança. Um plano do Terraform mostra a diferença entre a infraestrutura desejada e a real — esse modelo muda a forma de pensar sobre configuração.

## Destaques

- Um `terraform apply` provisiona um site completo no GitHub Pages
- Cria o repositório, ativa o Pages, configura o CNAME e gera o workflow de CD
- Provisiona os três subdomínios do hackathon
- Idempotente — pode ser executado novamente com segurança

## Stack tecnológica

- **IaC:** Terraform ≥ 1.5
- **Provider:** integrations/github ~> 6.0
- **CI/CD:** GitHub Actions
- **Hospedagem:** GitHub Pages
