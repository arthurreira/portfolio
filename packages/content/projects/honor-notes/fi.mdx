## What I built

A notes app split into two independent services: a Next.js frontend and a separate Dockerized REST API backend. The separation is deliberate — the two repos share a TypeScript interface package so the API contract is type-safe on both ends. The frontend consumes the API over HTTP; the API handles all CRUD and persistence. Either service can be replaced or redeployed independently.

Features: create/read/update/delete notes, tag-based organisation, persistent storage via the API.

## What I learned

The main lesson was about the cost of service boundaries. With a monolith, sharing types is trivial. With two separate repos communicating over HTTP, you need to be intentional about the API contract — what shape do requests and responses have, and how do you keep both sides in sync when it changes? Managing a shared types package taught me why API versioning and clear contracts matter more than they seem in small projects.

## Architecture

- **Frontend** — Next.js app consuming the REST API, with a clean notes UI
- **Backend** — Containerized REST API (Docker) handling CRUD operations for notes
- Both services communicate via HTTP; the backend is independently deployable
- Fully typed API contract shared between frontend and backend
